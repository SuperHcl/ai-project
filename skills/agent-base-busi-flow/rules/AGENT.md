# Agent 通用规则手册（BizFlow-8）

> 本手册随 **BizFlow-8**（`agent-base-busi-flow`）通用 AI 业务开发流程仓发布，跨项目共享。

行为准则，用于减少 AI 编码常见错误。**项目特化约束写在业务服务侧 `.agent/AGENT.md`，并优先于本手册。**

## 1. 先想再写

**不假设。不隐藏困惑。暴露权衡。**

动手编码前：
- 明确陈述你的假设。不确定时开口问
- 存在多种解读时，列出选项等用户确认——不要自己默默选
- 发现有更简单方案时直接提出，该 push back 就 push back
- 遇到不清晰的地方停下来，说出困惑点，等澄清

自检：改动前，你是否能一句话说清"要解决什么问题"？

## 2. 最小代码量

**只写解决问题必需的代码。零投机。**

- 新增方法前，必须先搜索项目中是否已有相同/相似功能可复用。能复用则复用，禁止为已有功能新建方法
- 单个方法禁止超过 30 行（不含注解和空行）。超限则拆分或简化逻辑
- 已有代码需要扩展时，优先修改已有方法兼容新场景，禁止新建并行方法导致逻辑分裂
  - 错误示范：已有 `processOne()` → 新建 `processBatch()`，两套逻辑各走各的
  - 正确做法：`processBatch()` 作为主实现 → `processOne()` 委托 `return processBatch(singletonList(x)).get(0)`

## 3. 精准改动

**只动必须动的。清理只限你自己制造的问题。**

编辑已有代码时：
- 不"顺手改进"相邻代码、注释、格式
- 不重构没坏的东西
- 遵循已有代码风格，即使你偏好不同
- 发现无关死代码，报告但不删除

你的改动产生孤儿时：
- 只清理你自己的改动导致的未使用 import/变量/方法
- 已有的死代码不要碰，除非明确要求

检验：diff 中每一行都能直接追溯到需求。

## 4. 目标驱动

**定义可验证的成功标准。循环直到通过。**

把任务转化为可验证目标：
- "加验证" → "先写测试让无效输入失败，再让测试通过"
- "修 bug" → "先写测试复现 bug，再让它通过"
- "重构 X" → "确保重构前后测试都绿"

多步骤任务先输出简要计划：
```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
```

强标准让你独立循环。弱标准（"搞出来就行"）需要不断停下来确认。

## 5. 架构边界

**代码不出让给 LLM。** 路由逻辑、重试策略、状态码判断——这些是确定性逻辑，必须用代码实现，不能用"让 AI 判断"替代。

**不跨模块侵入。** 跨模块需求走 RPC/Feign 接口调用，不直接在对方模块里加代码。

**模块只读/只写约束以业务服务侧 `.agent/AGENT.md` 为准**（如某模块禁止写库等），本通用手册不预设。

## 6. 编码基线加载

**编写 Java 代码前必须加载 `busi-coding-rules` Skill**。该 Skill 提供两类内容：

1. 《阿里巴巴 Java 开发手册》【强制】条款作为基线
2. AI 编码通病防护（人类少犯但 AI 常犯的错）

**本 Skill 不锁死技术选型**。工具类（Hutool / Apache Commons / Guava）、分层模式、字段命名、鉴权注解等项目习惯由业务服务侧 `.agent/coding-rules.md` 定义，优先级高于本 Skill。

## 7. 自动测试

**测试代码必须实际运行，不允许"看起来能跑"。**

- 编码完成后，必须生成并运行对应功能的测试用例（默认 Karate）
- 修复 Bug 时，先写测试复现问题，再修复并确认测试通过
- 新增/修改 API 时，必须补充对应测试用例并执行验证
- 测试项目位置由业务服务侧 overlay 指定（如 `xyk-api-test/`）

## 8. 文档输出规范

- 用"必须/禁止"，不用"建议/尽量"——消除模糊空间
- 不写 AI 腔（如"在数字化浪潮中""赋能"等空话）
- 后果写可观测影响（"请求超时会返回 504"），不写抽象描述
- TODO 必须标注责任人，无责任人的 TODO 等于没有

## 9. Windows 终端硬约束

**默认运行环境为 Windows + PowerShell。禁止使用 Linux/Bash 专属命令。**

- 语句分隔符用 `;`，禁止用 `&&`（PowerShell 不支持 `&&`）
- 禁止使用 `grep` → 用 `Select-String` 或内置 Grep 工具
- 禁止使用 `cat` → 用 `Get-Content` 或内置 Read 工具
- 禁止使用 `rm` → 用 `Remove-Item`
- 禁止使用 `cp`/`copy` → 用 `Copy-Item`
- 禁止使用 `mv` → 用 `Move-Item`
- 禁止使用 `ls` → 用 `Get-ChildItem` 或内置 Glob 工具
- 禁止使用 `find` → 用内置 Glob/Grep 工具
- 禁止使用 `mkdir -p` → 用 `New-Item -ItemType Directory -Force`
- 项目已有 `.bat`/`.ps1` 脚本时，优先直接调用脚本而非手写命令
- 路径使用反斜杠 `\` 或正斜杠 `/`（PowerShell 两者兼容），禁止用 `~` 表示主目录

> 跨平台部署时，业务服务侧 `.agent/AGENT.md` 可覆盖此规则。

自检：终端命令发出前，是否每个命令都在 PowerShell 中合法？

## 10. 禁止遗留临时文件

任务结束时确认工作区干净：**无调试脚本、无临时输出、无未跟踪文件。**

## 11. 流程编排入口

**首次接入新项目时，先执行 `busi-project-init` Skill 初始化 `.agent/` overlay 文件**（`AGENT.md` / `coding-rules.md` / `overlay-spec.md`）。安装脚本 `install.ps1` 会检测缺失并提醒。overlay 未就绪时 B2-B9 各 Skill 缺少项目特化约束，产出质量下降。

**业务版本开发的统一入口是 `busi-flow-orchestrator` Skill**。识别以下触发词后，先加载该 Skill 而不是直接动手：

- 启动类："开始 v{X} 开发" / "启动 v{X}"
- 恢复类："继续" / "v{X} 进展" / "状态"
- 控制类："重做 B{N}" / "跳过 B{N}" / "暂停"

该 Skill 维护 `iterate/v{X}/.flow-state.json` 持久化进度，调度 B2-B9 链路，并把守 5 道人工审查检查点（C1-C5）。**禁止绕过 orchestrator 直接写需求 / 接口 / 代码** —— 所有产物必须挂在某一步 B{N} 名下，便于审计与中断恢复。

---

**这些规则在生效，如果：** diff 精简、没有顺手改动、没有过度设计、困惑在编码前就提出来而不是在犯错后才发现。

01

创作背景

为什么要有这套东西？—— 从一次真实的痛感出发

01 · 创作背景

现状：对话式使用 AI，没有形成流程

目前在用 AI 做功能开发时，典型的工作方式是这样的：

STEP 1
粘贴需求文档
整段文字喂给 AI
→
STEP 2
AI 自行理解
对比现有代码
→
STEP 3
给出实现逻辑
直接开始写
→
STEP 4
来回调整
反复改 N 轮
方式粗糙
需求没有结构化解析，AI 理解靠"悟性"，遗漏与误读频发
不符合预期
代码风格、包结构、项目规范全不对，需要人类反复纠正
没有沉淀
每次开发都是从零对话，上次踩过的坑下次再踩一遍
01 · 创作背景

这种方式的实际效果

70% ~ 80%
最终成果预估只能达到预期效果的比例
剩下 20%~30% 靠人类手工补齐
痛点归因
  • 需求直接进入编码，缺少澄清环节，理解偏差到代码层才暴露
  • AI 不知道项目的结构、规范、约束，产出与环境格格不入
  • 没有审查卡口，错误一路传导到测试甚至上线
  • 过程无文档沉淀，经验无法复用，下次迭代重来
  • 对话状态易丢失，中断后无法恢复进度
根因不是 AI 不够聪明，而是我们把"人用的开发流程"省略了，直接让 AI 跳到了编码。
02

原始想法

如果 AI 能像人一样，走完一套标准开发流程呢？

02 · 原始想法

核心思考：一个朴素的问题

如果能够把 AI 建设成一个标准的、高效的、人为操作少的辅助工具呢？
参照系：人类开发者的标准流程
一个靠谱的人类开发者拿到需求后，不会立刻写代码——他会先读需求、问问题、画设计、评审、再编码、再测试、最后总结。

这套流程是几十年软件工程沉淀下来的质量保障体系。AI 也应该走同样的路。
两个关键转变
  • 从"聊天"到"流程"：把一次性对话，变成有阶段、有产物、有卡口的流水线
  • 从"AI 猜"到"AI 问"：不确定的地方主动反问人类，而不是自己默默假设
预期不是让 AI 取代人，而是让人只在关键决策点出现，其余环节 AI 自动流转。
02 · 原始想法

最初设想的 8 个预期（第一版草图）

创作之初写下的预期流程 —— 以人类角度制定的标准开发流程：

  • 1. AI 自己解析需求文档并进行分析
  • 2. 对需求提出疑问，与人类一问一答，直到完全理解
  • 3. 输出接口文档（评估需要接口的话）
  • 4. 输出符合《项目规范》的设计文档 —— 给人看（前端 / 测试）
  • 5. 输出更符合 AI 理解的设计文档 —— 给 AI 看（若与人版趋同可合并）
  • 6. 开始编码，符合项目结构与编码规范（规则由人类制定）
  • 7. 单元测试、整体测试
  • 8. 需求总结、改动总结 —— 沉淀给下次迭代
回头看：这份草图与最终落地几乎一一对应
预期 1~8 → 落地为 B2~B9 八个流程 Skill；其中第 5 步"AI 版设计文档"被保留为独立产物（B6 AI 开发规格书），实践证明两份文档读者不同、粒度不同，没有合并。
02 · 原始想法

达成预期的前提 & 建设目标

前提：AI 需要先"认识"项目

  • AI 需要知道项目的结构和规范才能写出合群的代码
  • 通过全局分析对项目做了解和沉淀：wiki、AGENTS 文件等
  • 包结构、分层模式、编码规范、硬约束 —— 人类制定规则，AI 遵守规则
这就是后来的 .agent/ overlay 机制：项目特化知识以文件形式注入，通用流程不污染。

四个建设目标

① 先建通用流程
做一个项目无关的、符合预期的 agent 流程骨架
② 一键应用到业务服务
类似 QuickStart 的一键安装，先把基础能力建设好（设计模板、编码规范），再执行各步骤
③ 步骤借力"工具类"
各步骤使用或创建通用 Skill / MCP 之类的工具能力
④ 人类把握边界
不确定的点通过 grill-me 式 QA 及时咨询人类，规则与边界由人制定
02 · 原始想法

设计参考：站在成熟方案的肩膀上

参考 1 superpowers 架构
建设过程中参考 superpowers 的架构与实现方式：
  • Skill 化组织：每个能力一个独立 SKILL.md，关键词触发
  • 渐进式披露：不一次性堆全量上下文，用到才加载
  • 元技能调度：由一个总控 Skill 编排其他 Skill
参考 2 grill-me 拷问机制
流程中需要人类制定规则、边界的环节，采用 grill-me 式一问一答：
  • 逐题拷问：一次 1~3 个强相关问题，不甩问题清单
  • 每题带推荐答案：并说明理由与影响面
  • 答到共识为止：所有不确定点落到文档，不留模糊
这两条参考直接塑造了 BizFlow-8 的形态：Skill 化的流程步骤 + 贯穿全程的澄清交互。

方案总览

BizFlow-8 是什么？一套项目无关的 AI 开发协作骨架

03 · 方案总览

BizFlow-8 = 业务流（BusinessFlow）+ 8 步流程

物理仓库名 agent-base-busi-flow，沟通 / 文档 / PR 标签统一用别名 BizFlow-8

一句话定义
Java / Spring 技术栈下的标准化 AI 协作开发 SOP，支撑 "需求解析 → 澄清 → 接口文档 → 前置设计 → 编码 → 测试 → 沉淀" 完整 8 步流程。

项目无关 —— 让 AI 在不同业务服务里都能按同一套流程办事。
仓库里有什么
  • rules/ — 跨项目通用的 Agent 行为准则（自动加载）
  • skills/ — 9 个流程 Skill + 1 个总编排 + 1 个项目初始化
  • templates/ — 版本迭代交付物模板（项目无关）
  • scripts/ — QuickStart 一键安装脚本 install.ps1
  • docs/ — 流程总览与安装指南
03 · 方案总览

架构核心：通用仓 + 业务侧 overlay 注入

通用流程不下沉业务知识；项目特化内容通过业务服务侧 .agent/ 注入，不污染通用仓库

通用仓 agent-base-busi-flow
  • 8 步流程怎么走（Skill 逻辑）
  • 行为红线与文档规范（rules/AGENT.md）
  • 阿里 Java 手册强制条款基线
  • AI 编码通病防护
  • 版本产物模板（项目无关）
一份维护，全公司项目复用
业务服务侧 .agent/ overlay（3 个文件）
  • AGENT.md — 模块边界、包路径前缀、接口前缀、文档落地位置
  • coding-rules.md — 工具选型、分层模式、BaseEntity、鉴权、Feign 归口
  • overlay-spec.md — iterate 根目录、版本号规则、测试框架
项目特化约束，优先级高于通用规则
overlay 未就绪时各 Skill 缺少项目特化约束（包路径、分层模式、文档位置），产出质量会下降 —— 所以安装后第一件事就是初始化 overlay。
03 · 方案总览

设计哲学：四条核心理念

上下文即稀缺资源
Skill 只记 Agent 无法从代码推断的隐式知识（规则、约定、边界），能从代码读出来的一律不写，避免上下文膨胀
渐进式披露
关键词触发才加载对应 Skill，不一次性堆全量上下文；模板抽离到 references/，触发即吃的上下文密度提升 2.2×
人工审查检查点
设计评审 / 接口骨架评审 / 测试通过等 5 道卡口，AI 不擅自越过；人类只在关键决策点出现
三条红线
先想再写（不假设、暴露困惑）、最小代码量（零投机、复用优先）、精准改动（diff 每行可追溯到需求）

04 · 核心机制

起步：初始化 → 解析需求 → 澄清

0
项目初始化（前置，不属于 8 步链）
busi-project-init · 触发词："初始化项目"
职责：检测并生成 .agent/ 下 3 个 overlay 文件；自动探测项目结构（模块 / 包路径 / 技术栈），交互式询问关键信息，生成带预填值的 overlay
1
解析需求
busi-req-analyze · 触发词："解析需求"、"分析需求文档"
输入：.docx / .md 文件、Confluence 链接、粘贴文本、口述需求 输出：iterate/v{版本}/01-需求内容.md —— 结构化需求（背景 / 目标 / 范围 / 验收标准 / 待确认事项）
2
澄清交互 关键差异化能力
busi-req-clarify · 触发词："澄清需求"、"需求拷问"
风格：参考 grill-me，一次 1~3 个强相关问题，每题带推荐答案 + 影响面，答完即落库 输出：需求文档中所有 ❓ 全部确认，Q&A 归档
不替用户拍板：回答含糊时复述确认，仍含糊则标记留下
04 · 核心机制

契约：接口文档 → 人类设计文档

3
接口文档 出口设 C1 卡口
busi-api-spec · 触发词："接口文档"、"接口设计"
定位：只产"契约"不产"实现" —— 方法签名 / 路径 / 出入参 / 鉴权 / 错误码 输出：02-接口文档-内部.md（前端 HTTP 调用）+ 02-接口文档-外部.md（跨服务 Feign）
签名锁定后前端可并行 mock 开发可选双产物：同步生成 Form/VO/Controller 占位代码
4
人类设计文档 出口设 C2 卡口
busi-design-doc · 触发词："设计文档"、"design doc"
读者：前端 / 测试 / 后端 reviewer —— 讲"为什么这么做"，图为主 内容：业务流程图、时序图、数据模型 ER/DDL、字段中文释义、状态机、决策权衡、异常边界、测试要点
DDL 边界：人类提供的既有表结构 AI 仅自审不擅改，违例汇总待 C1 裁决
设计评审（C2）由前端 + 测试 + reviewer 三角度会审 —— 通过后才允许进入编码准备阶段。这是质量最关键的一道闸门。
04 · 核心机制

落地：AI 规格书 → 编码循环

5
AI 开发规格书 专给编码 AI 看
busi-dev-spec · 触发词："写规格书"、"dev spec"
定位：把前面所有产物收敛成工程装配清单 —— 文件级路径、类与方法签名、实施顺序（编译可过的拓扑序）、TDD 用例清单 强约束：不重抄 B5 内容（DDL / 权衡 / 流程图全部引用回 B5），只产 B5 没给的东西
6
编码循环 出口设 C3 卡口
busi-dev-loop · 触发词："接口骨架"、"开始开发"
阶段 0 接口骨架：仅生成 Controller 签名 + VO/DTO/Form，mvn compile 通过 → 人工小卡口确认契约 阶段 1+2 TDD 红绿：单功能小步循环（编码 → 编译 → 测试 → 提交），自动加载 busi-coding-rules
协同：test-driven-development 卡死 2 轮 → systematic-debugging 提交前 → verification-before-completion
内置 AI 死循环脱困机制：编译 / 测试失败 ≥2 轮时强制系统性排查，禁止盲改；跑通验证命令才允许宣称"完成"。
04 · 核心机制

收官：集成测试 → 总结沉淀

7
API 集成与回归测试 出口设 C4 卡口
busi-api-test · 触发词："生成测试"、"接口测试"
范围：端到端链路 / 跨需求集成 / 历史回归 / 边界压测（不重复 B7 单测） 方式：默认 Karate，最大 3 轮修复循环；失败分类处理 —— 代码 Bug / 用例问题 / 设计缺陷（设计缺陷回退 B4/B5）
8
总结沉淀 push 前设 C5 终审
busi-iter-summary · 触发词："迭代总结"、"沉淀"、"收官"
5 个职责：完整性审计（B2-B8 产物齐不齐）→ CHANGELOG 生成 → 遗留待澄清沉淀 → AI 自反思踩坑 → 统一 git push 产出：迭代总结（需求实现回顾 / 改动清单 / 设计与实现差异 / 下次迭代 AI 该知道的事）
B7 只 commit 不 push —— 由 B9 统一推送，避免半成品上 main
前 7 步关注"做对单个版本"，第 8 步关注"沉淀给下个版本" —— 这是经验可复用、AI 越用越聪明的关键。
04 · 核心机制

为什么要两份设计文档？

原始想法中的疑问："AI 的和人类的设计文档如果差不多就合并" —— 实践证明不能合，读者与粒度完全不同

B5 人类设计文档 —— 给人看
  • 讲"为什么这么做"：背景、权衡、取舍
  • 图为主：流程图 / 时序图 / ER / 状态机
  • 读者：前端拿契约与状态、测试拿用例边界、reviewer 审方案
  • 评审会上被逐行挑战的文档
B6 AI 开发规格书 —— 给 AI 看
  • 讲"具体怎么改"：路径 + 签名 + 约束
  • 清单为主：文件路径级清单 / 类方法签名 / 编译可过拓扑序 / TDD 用例
  • 读者：B7 编码 AI —— 表达更刚性、粒度更细
  • 不重抄 B5：已有内容一律引用，避免双写漂移
一句话区分：B5 说服人，B6 驱动机器。若合并，人会嫌啰嗦、AI 会缺约束。
04 · 核心机制

5 道人工审查检查点 —— 人类的存在感在这里

编号位置主审角色检查重点
C1B4 接口文档出口后端 reviewer + 前端接口路径 / 字段类型 / 鉴权 / 错误码
C2B5 设计文档出口前端 + 测试 + reviewer 三角度DDL / 决策权衡 / 异常 6 类 / 测试要点
C3B7 编码出口（含阶段 0 骨架小卡口）reviewer编码 + 单测全过 / 实施顺序符合规格书
C4B8 集成测试出口测试 + reviewer集成测试全绿 / 覆盖矩阵 5 类齐
C5B9 push 之前用户最终决定者完整性审计 / CHANGELOG / 无遗留 ❓
统一展示模板
每道卡口按固定格式输出：本步产物 → 自检通过项 → 遗留待跟进 → 建议主审角色 → 等用户回复 "OK" 或 "不过 + 意见"
绝对禁止
跳过检查点自动进入下一步。即使用户连续说"继续"，到达卡口时编排器必须强制停下等显式确认 —— 防"一路冲到上线"事故。
04 · 核心机制

流程编排器：让 3 天后的你能接上进度

busi-flow-orchestrator —— meta-skill，只调度不干活：不产需求 / 不写代码 / 不写测试

① 入口路由
"开始 v2.33.0 开发" → 创建版本目录 + 状态文件 → 跳 B2；"继续" → 读状态跳转到当前步骤
② 进度持久化
iterate/v{X}/{模块}/.flow-state.json 记录当前步骤、已完成清单、卡口历史、阻塞项 —— 中断 3 天也能秒恢复
③ 卡口把关
5 道检查点统一模板展示；重做 / 跳过需显式理由并留痕，跳过项在 B9 审计中显式列出
# "状态" / "进展" 随时查看可视化进度 [✅] B2 解析需求 [✅] B3 澄清 [✅] B4 接口文档 (C1 通过) [🔄] B5 设计文档 (等待 C2 审查) [ ] B6 规格书 [ ] B7 编码 [ ] B8 测试 [ ] B9 收尾 ⚠ 待澄清遗留 (1)：[BLK-1, high] X 字段是否需脱敏（来自 B3） ▶ 下一步：等待 C2 审查 —— 审完说 "OK" 放行，或 "不过 + 意见" 驳回
跨会话恢复：新会话发现未完成的 .flow-state.json 会主动询问"继续开发还是开始新任务"，不擅自继续。
04 · 核心机制

行为准则：rules/AGENT.md 的三条红线

先想再写
不假设、不隐藏困惑、暴露权衡。多种解读列选项等确认；更简单方案直接 push back。自检：能一句话说清"要解决什么问题"吗？
最小代码量
只写必需的代码，零投机。新增方法前必须先搜已有实现；单方法 ≤30 行；扩展优先改已有方法，禁止并行方法导致逻辑分裂。
精准改动
不顺手改相邻代码、不重构没坏的东西、遵循已有风格。检验：diff 每一行都能直接追溯到需求。
其余硬约束（共 11 条）
  • 目标驱动：任务转化为可验证标准，循环直到通过
  • 架构边界：确定性逻辑必须用代码实现，不出让给 LLM 判断
  • 写 Java 前必加载 busi-coding-rules（阿里手册强制条款 + AI 通病防护）
  • 测试必须实际运行，禁止"看起来能跑"
  • 文档用"必须/禁止"不用"建议/尽量"，消除模糊空间
这些规则在生效的标志
  • diff 精简，没有顺手改动
  • 没有过度设计
  • 困惑在编码前就提出，而不是犯错后才暴露
项目特化约束写在业务侧 .agent/AGENT.md，优先级高于通用手册。

06 · 落地与演进

Before / After：这套流程带来了什么

Before · 对话式开发
  • 需求直接进编码，理解偏差代码层才暴露
  • AI 不懂项目规范，产出格格不入
  • 无审查卡口，错误一路传导
  • 无文档沉淀，经验随对话蒸发
  • 中断即丢失，无法恢复
  • 达成率约 70%~80%
After · BizFlow-8 流程化开发
  • B3 澄清把理解偏差消灭在编码前
  • overlay 注入项目规范，产出即合群
  • 5 道卡口，人类在关键点把关
  • 8 类产物归档，经验跨版本复用
  • 状态文件持久化，随时中断随时续
  • 流程可追溯：代码 → 规格 → 设计 → 需求
本质变化：把 AI 从"聊天对象"变成"流水线上的靠谱同事" —— 人类制定规则与边界，AI 在规则内高效运转。
BIZFLOW-8 · Q & A

让 AI 按人类的标准流程做开发

从一次"对话式开发只有 70 分"的痛感出发，到一套可安装、可恢复、可审计、可沉淀的 8 步流程。 BizFlow-8 不是要替代工程师的判断，而是把工程师的判断固化成流程与规则，让 AI 在框架内把事情做对。

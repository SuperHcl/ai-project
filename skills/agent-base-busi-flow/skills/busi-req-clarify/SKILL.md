# 需求澄清

## 触发条件

- 用户说"开始澄清"/"clarify 一下"/"答疑"
- `busi-req-analyze` 完成后用户确认进入
- 文件 `iterate/v{版本}/01-需求内容.md` 第六章"待确认事项"非空

## 核心交互原则

| 原则 | 说明 |
|---|---|
| **逐题问** | 一次最多 1-3 个**强相关**问题（用 `AskUserQuestion`，每问 ≤4 个选项）。**禁止甩 10 个问题**让用户一次性答完 |
| **每题必有推荐** | 选项里推荐项加 `(Recommended)`，并在描述中说明**理由**（基于业务一致性 / 历史决策 / 性能 / 兼容性等） |
| **每题必给影响面** | 选 A 会导致 X，选 B 会导致 Y。**不能写"性能更好"这种空话**，要写"减少 N 次远程调用"/"需新增表 Z"等具体后果 |
| **答完即落地** | 用户每回答一组，**立刻** `SearchReplace` 把 ❓ 替换为确认值，并从第六章移除该条。不要攒到最后批量改 |
| **不替用户拍板** | 用户答得含糊（"都行"/"看你"）→ 复述推荐答案 + 影响面再确认 1 次；仍含糊则标 ⚠️ 留下，**不要自己定** |

## 步骤

### 步骤 1：读现状

`Read` 当前 `iterate/v{版本}/01-需求内容.md`，定位第六章。

### 步骤 2：分组排序

按以下优先级对待澄清项排序：

1. **数据模型未定**（字段类型 / 枚举值 / 主键策略）—— 这些不定后面 B5 设计文档没法做
2. **业务规则未定**（边界条件 / 互斥关系 / 默认值）
3. **历史兼容未定**（老数据如何 migrate / 灰度策略）
4. **UI/交互细节**（一般可推迟，标注"前端 owner"则跳过）

**强相关的题合并问，弱相关的拆开问。**

### 步骤 3：逐组提问

用 `AskUserQuestion` 工具，单题模板：

```
question: "审批范围'全部'如何存储？"
options:
  - label: "存 3 条记录 (Recommended)"
    description: "template_type=1/2/3 各一条。查询直接 IN，无需特殊判空。后续新增类型不影响。"
  - label: "存 1 条记录 type=0 表示全部"
    description: "节省 2 行存储，但查询需 OR 判断 type=0；新增类型时'全部'语义需重新评审。"
  - label: "增加单独的 is_all 标志位"
    description: "直观，但与 type 字段冗余；scope 表多 1 列；新增类型仍需评审。"
```

**最多 4 个 options**（`AskUserQuestion` 工具限制）。选项过多就拆题。

### 步骤 4：答完即落地

用户每答一组：

1. **复述确认**："你选的是 A — 存 3 条记录。如果有问题现在打断我。"（仅在用户答案与推荐不一致 / 含糊时才复述）
2. `SearchReplace` 修改 `iterate/v{版本}/01-需求内容.md`：
   - 把对应章节里的 ❓ 替换为确认值
   - 从第六章移除该条（标记为 ✅ 并归入"已确认事项汇总"表）
3. **检查派生问题**：答案 A 是否带来新的待澄清项？有就追加进第六章，下轮继续问。

### 步骤 5：循环直到清空

第六章空（或仅剩 ⚠️）→ 输出汇报：

```
澄清完成：
- 共澄清 N 项 → 已落到 §六.已确认事项汇总
- 剩余 M 项 ⚠️（用户未明确，保留待开发期再决）
- 派生新待澄清 K 项（已并入下轮）

是否进入 `busi-api-spec` 输出接口骨架？
```

**不自动跳转**，等用户确认。

## 反模式（AI 在此环节最常犯）

### 1. 一次性甩 N 个问题

❌
```
1. 字段 A 类型？
2. 字段 B 是否可空？
3. 枚举 C 值域？
4. 是否支持灰度？
5. 老数据如何迁移？
…
```

✅ 一次 1-3 个**强相关**的，答完再问下一组。

### 2. 推荐答案不给理由

❌ "推荐 A。"
✅ "推荐 A — 因为现有 `xxxService.findByType()` 方法已按此假设实现，选 B 需重写 + 数据迁移。"

### 3. 影响面写空话

❌ "选 A 性能更好。"
✅ "选 A：每次查询少 1 次 Redis 调用（约 2ms）；选 B：需新增 `xxx_cache` 表，初始化数据约 10w 行。"

### 4. 诱导性提问

❌ "你应该是想用方案 A 对吧？"
✅ "A / B / C 三个方案，推荐 A，理由 …，影响 …。请选。"

### 5. 把模糊回答当决策

用户回 "都行 / 看你 / 你定"：
- 第 1 次：再次复述推荐 + 影响面（"那我按推荐 A 走，影响是 X，确认吗"）
- 仍模糊：**标 ⚠️ 留在第六章**，开发期再决，**不自己拍板**

### 6. 越权创造选项

原文 / 推荐答案池外的选项不要自己造。如果你觉得需要第 4 个方案，**先和用户说**："我想加个方案 D：…，可以吗？"

### 7. 不落地

答完一题不立刻写文件，等积攒到最后批量改 → 用户中途打断或会话中断，**全部丢失**。

## 与 grill-me 的区别

| 维度 | grill-me | busi-req-clarify |
|---|---|---|
| 目标 | 验证设计/技术决策 | 落地业务需求字段值 |
| 产出 | 对话本身（共识在脑子里） | 文件落地（`01-需求内容.md` 第六章 ✅） |
| 范围 | 自由话题树 | 已限定为第六章列出的待澄清项 |
| 终止 | 设计共识达成 | 第六章清空或全部 ⚠️ |

## 业务服务侧 overlay 可补充

| 内容 | 用途 |
|---|---|
| 推荐答案知识库 | 项目历史同类决策（如审批模型 / 软删除策略 / ID 类型）的固定推荐 |
| 必问清单 | 项目级红线（如"必须问数据隔离策略"），未问到则不允许进 B4 |
| 澄清记录归档位置 | 默认归到 §六.已确认事项汇总；项目可指定单独归档目录 |

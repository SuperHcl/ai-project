# API 集成与回归测试

## 定位

**8 步流程的第 7 步，第四道人工审查检查点的依据**。

| 测试层 | 归属 |
|---|---|
| 单元测试（mock 依赖、覆盖单方法分支） | B7 内嵌（TDD 红绿） |
| **集成测试（真实 Spring 容器 + 真实 DB / 中间件）** | **B8** |
| **API 端到端（多接口数据依赖链）** | **B8** |
| **跨需求回归（本版本接口 + 历史接口受影响面）** | **B8** |
| **边界压测（B5 §九最后两类：分页极限、批量上限）** | **B8** |
| 全链路 / 性能 / 安全压测 | 不在本流程，由专项团队做 |

## 前置条件

- B7 已完成且**所有单测通过**（不能在编译都不过的代码上跑集成）
- 应用可启动到本地 / 测试环境（profile / 端口 / 外部依赖由 overlay 指定）
- 测试账号 / 测试数据 / 鉴权 token 已就绪
- 测试框架已选定（默认推荐 **Karate**，业务服务侧 overlay 可换 RestAssured / JUnit+WireMock / Postman+Newman）

## 输入

- B4 产物：`接口文档/{内部,外部}/*.md`（接口契约）
- B5 §九测试要点 + §七异常 6 类
- B6 §六 TDD 单测清单（避免重复，B8 只补单测覆盖不到的）
- 业务代码本体（实际实现）
- 业务服务侧 `.agent/coding-rules.md` 取测试框架与启动方式

## 输出

```
iterate/v{版本}/test/
├── 00-TEST-SPEC.md          ← 索引（链路图 + 模块清单）
├── 01-{需求}-TEST-SPEC.md   ← 单需求测试规格
├── ...
└── qa/
    └── 0{n}-{需求}-test-qa.md  ← 拷问归档
```

实际测试用例代码落到业务服务的测试目录（路径由 overlay 指定，如 `src/test/java/.../iterate/v{版本}`）。

## 三阶段流程

### 阶段 1：链路与范围识别

针对每个需求，AI **先读代码 + B4 接口文档** 产出三层数据，提交用户确认：

#### 1.1 端点清单

读改动涉及的 Controller / Feign，提取：路径、方法、入参类型、出参类型、鉴权注解、是否 Feign 跨服务。

#### 1.2 鉴权与路由识别

识别鉴权机制（具体注解名 / 中间件由 overlay 给，**不写死** `@InnerToken` / `@SaCheckLogin`）。区分：
- 内部接口：哪种 token？什么角色 / 权限可调？
- 外部接口（Feign / 第三方）：调用方身份如何模拟？

#### 1.3 调用链路图

```
链路：{业务流程名}
1. GET /xxx/list      → 拿 xxxId
2. POST /yyy/create   → 用 xxxId 创建（数据依赖：xxxId）
3. GET /yyy/detail    → 验证状态（数据依赖：yyyId）
4. POST /yyy/approve  → 审批（数据依赖：yyyId，角色切换）

数据依赖链：xxxId → yyyId
角色切换点：步骤 3→4 需切换 token（普通用户 → 审批人）
```

**强约束**：链路必须覆盖**至少一条主流程 + 一条异常分支**。

---

### 阶段 2：5 维拷问（每条链路）

> 一次一个问题，每个附推荐答案。维度顺序固定：1 → 2 → 3 → 4 → 5。

#### 维度 1：前置依赖验证（**必答，首位**）

未通过此维度，后续拷问无意义。

- 测试账号 / 角色 / 权限是否匹配被测接口要求？
  → 推荐：查 DB 或调用既有接口确认账号属性
- 鉴权方式是？token 怎么拿？
  → 推荐：读 Controller 注解 + 从测试基础设施取
- DB 是否有足够的前置测试数据？
  → 推荐：调查询接口确认非空，或写种子数据脚本
- 加密 / 脱敏字段如何处理？
  → 推荐：通过 API 取（不要直接 SQL 猜原文）

#### 维度 2：业务假设质疑

- 当前接口隐含哪些业务状态前提？（如"必须先 X 才能 Y"）
  → 推荐：读 Service 层入口 check 方法，提取前置状态校验
- 这些前提**违反**时接口返回什么？错误码和消息精确到什么？
  → 推荐：追踪 check 失败的异常抛出路径

#### 维度 3：数据链追踪

- 完整 SQL JOIN 链 / 跨服务调用链是哪些？哪些环节可能断？
  → 推荐：读 Mapper / Feign 调用，标记可空外键 / 可能为空的下游
- API 返回空时，是"数据不存在"还是"链路断了"？
  → 推荐：分别构造两种场景，断言要能区分

#### 维度 4：失败模式枚举

- 每条失败路径的错误码 / HTTP 状态码 / 消息**精确到什么**？
  → 推荐：列出 Service 所有异常分支，逐条断言
- 非法状态转换是否被拒绝（如终态再操作）？
  → 推荐：构造已是终态的数据，验证返回明确状态错误而非通用 500

#### 维度 5：断言校准

- 正确返回的具体**字段值**是什么？**为什么**这个值是对的？
  → 推荐：基于 DB 真实数据确定预期值，断言要编码 **WHY 业务逻辑**，不只是 `!= null`
- 如果业务逻辑变了，这个测试必须 FAIL 吗？
  → 推荐：变了还能 PASS = 测试无价值，必须收紧断言

用户说"完成" → Q&A 归档到 `qa/0{n}-{需求}-test-qa.md` → 产出 TEST-SPEC。

### 阶段 3：写用例 + 跑 + 修

#### 3.1 TEST-SPEC 三段式

**输出格式骨架见独立模板文件**：[`references/test-spec.template.md`](./references/test-spec.template.md)

模板含三段（链路总览 / 关键决策 / 用例矩阵）+ 用例覆盖矩阵硬约束（正向 ✅ / 边界 ✅ / 异常 ✅ / 兼容 ✅ / 跨需求回归 ✅，任一缺失即不合格）。落地时**必须读取该模板作为输出骨架**，不能凭记忆拼。

#### 3.2 写用例

按 TEST-SPEC §三逐条写，**禁止凭印象写"正向 + 几个错误"凑数**。

#### 3.3 跑测 + 修复循环

```
1. 启服务（按 overlay 指定的 profile / 端口 / 启动命令）
2. 跑测试（命令由 overlay 给）
3. 全过 → 进阶段 4
4. 有失败 → 分类（不允许盲改）：
   a. 代码 Bug → 调度 systematic-debugging → 回 B7 修 → 重新部署 → 回第 2 步
   b. 测试用例错（断言不准 / 数据不匹配）→ 修用例 → 回第 2 步
   c. 设计缺陷（缺接口 / 字段 / 状态）→ 暂停，回 B5/B6 改设计 → 用户确认后再回 B7
5. 连续 3 轮仍未过 → 强制暂停，触发 dev-loop 的死循环脱困机制
```

**设计变更判定**（任一即设计缺陷，不许就地凑实现）：
- 需新增 B4 没列的接口
- 需修改表结构
- 需修改 API 响应格式（影响前端）
- 修复范围超单方法 / 单类

#### 3.4 收尾 + 第四道人工审查检查点

```
集成测试已完成（第四道人工审查检查点）：
- N 个需求 / K 条链路 / M 条用例 / 全绿
- 覆盖矩阵：正向 ✅ / 边界 ✅ / 异常 ✅ / 兼容 ✅ / 回归 ✅
- 跑测命令：{命令}
- 报告：{路径}

请审核测试覆盖与断言精度后说"OK"，进入 B9（busi-iter-summary）做版本总结。
```

不自动跳。

## 与 B7 单测的边界（关键，避免重复）

| 维度 | B7 单测 | B8 集成 |
|---|---|---|
| 容器 | 不起 Spring | 起完整 Spring + DB + 中间件 |
| 依赖 | 全 mock | 真实 |
| 范围 | 单方法 / 单类 | 跨方法 / 跨服务 |
| 数据 | 内存 / mock | 真实 DB（含种子数据 + 清理脚本）|
| 速度 | 秒级 | 秒到分钟级 |
| 覆盖目标 | 分支覆盖 | 业务链路覆盖 |

**禁止在 B8 重复 B7 已覆盖的单方法分支断言**，B8 只看链路 / 跨服务 / 异常端到端。

## AI 反模式

1. **跳链路分析直接写用例** —— 阶段 1 没产出链路图就进阶段 3 → 必漏数据依赖 / 角色切换
2. **跳拷问** —— 5 维全跳 → 用例只测正向，异常断言全是 `!= null`
3. **断言只验非 null** —— `assert response.id != null` 而不是 `assert response.id == 期望值 && status == 期望状态` → 业务变了测试还过
4. **覆盖矩阵不全** —— 只有正向 + 1 个异常 → 不合格
5. **重复 B7 单测** —— 在集成里再断言一次单方法分支 → 浪费 + 维护成本翻倍
6. **设计缺陷凑实现** —— 发现缺接口直接现场加，不回 B5/B6 → 设计文档与代码再次脱节
7. **跑挂了改测试不改代码** —— 测试断言改宽以"通过" → 测试失去价值
8. **测试数据写死 token / 真实手机号 / 真实账号** —— 必有信息安全事故
9. **不清理种子数据** —— 跑一遍污染一次 DB → 后续跑测全部失败
10. **盲改循环** —— ≥3 轮失败不调 systematic-debugging，凭直觉改 → 触发死循环脱困

## 业务服务侧 overlay 必填

| 内容 | 用途 |
|---|---|
| 测试框架 | Karate / RestAssured / JUnit+WireMock / Postman+Newman |
| 启动命令与 profile | `mvn spring-boot:run -Pdev` / `gradle bootRun` 等 |
| 跑测命令 | `mvn test -Dkarate.options=...` / `gradle test --tests ...` |
| 鉴权 token 获取方式 | 走某个 /login 接口 / 从配置中心拿 / 测试账号清单 |
| 鉴权注解清单 | 项目实际用的注解（`@LoginRequired` / `@InnerCall` …）|
| 测试数据准备 | 种子 SQL 脚本路径 / 工厂方法 |
| 测试数据清理 | 跑后清理脚本 / 事务回滚机制 |
| 模块 baseUrl 映射 | 多模块项目每个模块的本地 baseUrl |
| 错误码体系 | 项目错误码定义文件，用于断言精度 |

# 需求解析

## 触发条件

用户提供以下任一形式的需求材料 + 一个版本号：

- `.docx` / `.md` / `.txt` 文件路径
- 粘贴的需求文本片段
- Confluence / Lark / Notion 等需求链接
- 口述需求（直接对话描述）

未给版本号时**主动问**（"这是 v 几？"），不要自己编。

## 步骤

### 步骤 1：读入原始需求

按材料形态分流：

| 输入形态 | 读取方式 | 失败回退 |
|---|---|---|
| `.md` / `.txt` | 直接 `Read` | — |
| `.docx` | 用 `python -c "from docx import ..."` 抽文本；**先确认环境有 `python-docx`**，没装就 `pip install python-docx -q` 再跑 | 仍失败时降级 `pandoc input.docx -t markdown`，再不行让用户**人工另存为 .md** |
| 网页链接 | `WebFetch` | 链接需登录时让用户**复制正文粘贴** |
| 粘贴文本/口述 | 直接读用户消息 | — |

> **不要假装读了**。读不到就如实说"读取失败，需要 X"。

### 步骤 2：识别版本目录与现有内容

- 路径为 `iterate/v{版本号}/{业务模块}/01-需求内容.md`（具体根目录由业务服务侧 `.agent/AGENT.md` 给出，未指定时用工作区根下 `iterate/`；业务模块名为中文可读名，如“国家模块”/“物料出口价格模块”）
- 一个版本可含 **N 个业务模块**，每个模块为一组紧密相关需求的集合（同一 BC 内、同一产品主题）。模块间设计/编码独立、模块内需求可多章节
- 若文件**已存在**：先 `Read` 全文，本次解析做**增量合并**（不是覆盖），把新需求追加到"需求清单"和对应章节
- 若文件不存在：按 §3 模板新建

### 步骤 3：抽取并填入模板

按以下结构填写（**所有字段都从原文抽取，不脑补**）：

```markdown
# {产品/服务名} V{版本号} 版本需求文档

> 文档版本：V{版本号}（需求分析中）
> 生成时间：{今天}
> 涉及模块：{从原文抽}
> 需求来源：{原文/对话给的，没说就空}
> 原型/附件：{链接，可选}

---
```

### 步骤 4：标记不确定

原文没说清的，**不要凭空补**，统一用以下符号：

| 符号 | 含义 |
|---|---|
| ❓ | 字段/规则在原文中未定义，需澄清 |
| ⚠️ | 原文表述存在多种合理解读 |
| 🔁 | 与历史需求/已有功能可能冲突，需 review |

每个 ❓ / ⚠️ / 🔁 都要进入第六章"待确认事项"对应条目，**不留悬空标记**。

### 步骤 5：写入文件

```
iterate/v{版本}/{业务模块}/01-需求内容.md
```

写完后**简要汇报**：
- 共抽出 N 个需求
- 共 M 个待澄清项
- 关键边界/冲突 N 条

最后**主动提示**："是否进入 `busi-req-clarify` 做一问一答澄清？"（不自动跳转，等用户确认）。

## 反模式（AI 在此环节最常犯）

1. **脑补字段**：原文没说的字段类型/枚举值不要自己定义。标 ❓ 让用户答。
2. **合并需求**：业务方写了 5 件事就拆 5 个章节，不要为了"看起来简洁"合并成 2 个段落——粒度丢失后续没法追溯。
3. **越界出方案**：本步骤只抽**业务诉求**和**字段含义**，不出 DDL、不画时序图、不挑技术选型——这些是 B5 设计文档的事。
4. **吞掉冲突**：原文与现有代码/历史需求矛盾时，**显式标 🔁** 进待澄清，不要"按自己理解的顺一遍"。
5. **简化表格**：业务给了 10 列字段就抽 10 列，不要"看起来差不多"压成 5 列。

## 业务服务侧 overlay 可补充

| 内容 | 用途 |
|---|---|
| `iterate/` 根目录位置 | 需求文档落地路径 |
| **业务模块命名规范** | 中文名 / 英文名 / 以 BC 为名等项目偏好 |
| 版本号命名规则 | `v2.30.0` / `R20260601` / 自定义 |
| 文档头部要求的额外字段 | 如负责人、PRD 链接、JIRA 单号 |
| 已有的需求模板/范例 | 项目原有规范优先 |

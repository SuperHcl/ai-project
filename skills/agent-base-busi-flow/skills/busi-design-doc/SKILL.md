# 设计文档（人类可读）

## 定位

**8 步流程的第 4 步，第二道人工审查检查点的依据。** 这是**编码前**的前瞻设计——锁定方案后，前端、测试、AI 开发可以并行展开。

> 与 kgd-doc 的 `xyk-design-doc`（编码后回顾型，5 维拷问验证代码真实性）**完全不同**。本 Skill 写的是"我打算怎么做"，不是"我做了什么"。

读者画像（4 类）：

| 读者 | 关心什么 |
|---|---|
| 前端工程师 | 接口契约（已在 B4）/ 状态机 / 字段流转 / 交互节点 |
| 测试工程师 | 用例边界 / 异常分支 / 状态流转 / 性能指标 |
| 后端 reviewer | 方案合理性 / DDL / 决策权衡 / 风险 |
| AI 开发（B7） | 数据模型 / 流程时序 / 决策结论（作为编码约束） |

## 输入

- `iterate/v{版本}/{业务模块}/01-需求内容.md`（已澄清）
- `iterate/v{版本}/{业务模块}/02-接口文档-内部.md` / `02-接口文档-外部.md`（已锁定签名）
- 业务服务侧 `.agent/AGENT.md`（拿 BaseEntity 字段、DDL 模板、字段命名规约）
- 现有代码（仅作为参考，了解既有架构和约束，不抄实现细节）

## 输出

```
iterate/v{版本}/{业务模块}/03-设计文档.md
```

模块内多需求拆分 → 在本文档内采用二级章节 `## A. {需求 1}` / `## B. {需求 2}` 结构，不再拆多文件。

> **形态默认 Markdown + mermaid**，理由：IDE 直接预览、diff 友好、GitLab/GitHub 自动渲染。需要 HTML 单文件（如分发给业务方）由 overlay 指定渲染脚本。

## 文档结构

**输出格式骨架见独立模板文件**：[`references/03-design-doc.template.md`](./references/03-design-doc.template.md)

模板含 10 节固定章节：背景范围 / 架构上下文 / 数据模型 / 关键流程 / 状态机 / 关键决策 / 异常边界 / 安全性能 / 测试要点 / 上线灰度。落地时**必须读取该模板作为输出骨架**，不能凭记忆拼。

## 步骤

### 步骤 1：读全输入

并行读 `01-需求内容.md` + 接口文档目录下所有文件 + `.agent/coding-rules.md`（拿 BaseEntity 字段 / 索引规约 / DDL 模板）。

### 步骤 2：按需求拆分

每个需求独立一篇设计文档（与 B4 接口文档的拆分粒度对齐）。

### 步骤 3：先列骨架再填内容

先写 10 节标题 + 每节一两句要点，让用户**先看骨架**再决定是否填详细内容。避免一上来 200 行让用户没法 review。

### 步骤 4：对每节填充

**必读** [`references/03-design-doc.template.md`](./references/03-design-doc.template.md) 作为输出格式骨架，按模板的 10 节顺序填充。

**严禁跳节**（先写第六章决策，再倒回去写第三章数据模型，会导致前后矛盾）。

**第三节数据模型 DDL 来源判定**（避免擅改人类已有结构）：
- DDL 由 **AI 自生成**（无既有表）：按业务服务侧 overlay 中的 DDL 规约（字段命名 / NOT NULL / DEFAULT / COMMENT / 索引）一次到位
- DDL 由 **人类已提供**（既有表 / DBA 给的脚本）：AI **只检查不擅改**——把发现的违例（命名 / 默认值 / 注释 / 索引等不合规约的项）汇总到本节末尾的 **《表结构提示项（AI 自审，待 R1 裁决）》** 子节，列出「列名 / 现状 / 违例类型 / 建议改法 / 风险等级」五列表格，由人类在 R1 评审时裁决，AI 不在文档外擅自动手改
- 高风险点（如取值范围与新规不符、与外部系统约定的字段语义冲突）须显式标注，提醒回写时评估存量业务逻辑影响

**第四节关键流程双轨制图表硬约束**（§4 不达标直接不合格）：
- 时序图 `sequenceDiagram`：描述"谁调谁"，仅画跨模块 / 跨服务交互
- 业务流程图 `flowchart TD`：描述"业务规则与异常分支决策"，**每条主流程都须各一张**
- 仅使用 mermaid 基础语法：方向 `TD`、`([])` 起止节点、`[]` 动作节点、`{}` 判断节点。**禁止 `style` 样式定义**
- 两者互补必备：跨模块通信看时序图，业务规则与异常分支看流程图，仅画其一、以及给出双图但在流程图里重复画成时序图，都不合格
- 状态流转另额外在§5 画状态机，不在§4 重复

### 步骤 5：合规自检

写完每篇对照 4 条自检：

1. ✅ 每个非平凡决策都写了"问题 + 可选方案 + 推荐 + 权衡"，不只是"做了什么"
2. ✅ 数据模型给出完整 DDL（含字段、注释、索引），不留 `...` 占位
3. ✅ 关键流程**双轨齐备**：跨模块交互画 `sequenceDiagram` + 业务规则/异常分支画 `flowchart TD`；有状态流转的另画状态机
4. ✅ 异常 6 类（空 / 并发 / 超时 / 权限 / 历史 / 灰度）至少都给了说法（N/A 也算）

任一不过 → 重写该节，**不要带病提交**。

### 步骤 6：输出完成

本模块设计文档写入 `iterate/v{版本}/{业务模块}/03-设计文档.md`。

### 步骤 7：人工审查检查点

写完后**主动告知**：

```
设计文档已完成 N 篇，进入【第二道人工审查检查点】。

请前端 / 测试 / 后端 reviewer 各角度过一遍，重点关注：
- 数据模型 DDL 是否完整、索引是否合理
- 关键决策是否权衡到位
- 异常 / 边界 / 性能是否考虑充分

确认无误后说"OK"，再进入 `busi-dev-spec`（AI 开发规格书）。
```

**不自动跳转**，等用户明确确认。

## AI 反模式

1. **写成实现指南** —— "Step 1: 创建 XxxService" 是 B6 / B7 的事，本文档只写决策和图
2. **决策只说做了什么** —— "用 Redis 缓存"不是决策，"为什么不用 caffeine 本地缓存 / 业务规模超 X 后切换" 才是决策
3. **图表单轨** —— 时序图（跨模块通信）与业务流程图（决策分支）**必须双轨齐备**，仅画其中一种直接不合格；状态流转另额外画状态机
4. **mermaid 加样式** —— `style A fill:#f9f` 一律删除，遵守通用 mermaid 规范（基础语法即可）
5. **DDL 不完整** —— 字段类型 / NOT NULL / DEFAULT / COMMENT / 索引五件套必须齐
6. **异常只列 happy path** —— 异常与边界章节必须显式给 6 类场景的回应（N/A 也算回应）
7. **跳节** —— 先写决策章再倒回去补数据模型，前后矛盾必现
8. **越界写代码** —— 不出 Java 代码片段（接口签名已在 B4，实现细节在 B6/B7），出 SQL DDL 是允许的
9. **状态机字段映射缺失** —— 画了状态机但没标 DB 值映射，前端 / 测试无法对齐
10. **擅改人类提供的 DDL** —— 既有表 / DBA 提供的脚本，AI 只检查不擅改；违例必须汇总到《表结构提示项》子节交 R1 评审裁决

## 业务服务侧 overlay 可补充

| 内容 | 用途 |
|---|---|
| 输出形态偏好 | 默认 Markdown，需要 HTML 时给渲染脚本（如 `pandoc` 命令） |
| DDL 模板 | 项目专用的 BaseEntity 字段、表前缀、索引命名规约 |
| 时序图模板 | 项目特定的角色（哪些是子模块、哪些是 SDK、哪些是外部系统） |
| 鉴权 / 数据隔离 模板段 | 项目固定的安全章节模板（如多租户隔离规则） |
| 灰度策略模板 | 项目灰度规则（按门店 / 按用户 / 全量） |

# 验收口径（一页）

> 写在 `.archguard/spec/<需求简称>.md`，不进仓库（该目录已自动排除）。
> 目的：让"做完了没有"有一个不需要读代码就能回答的答案。

```markdown
# 验收：<一句话>

## 谁用
- 端：员工端 PC / 员工端 App / 合作伙伴端 / 内部接口（/internal）
- 角色与数据范围：组织 / 公司 / 国家 / 供应商 / 本人（多选写清）

## 什么数据
- 来源表或外部系统：
- 量级：单条 / 百级 / 万级（决定要不要分页、要不要异步）
- 样例：贴一条真实或接近真实的数据

## 成功长什么样（可观测）
1. <例：提交后任务中心出现"待审批"，参与人可见>
2. <例：审批通过后单据状态变为"已生效"，并写一条操作日志>

## 失败怎么办
| 情况 | 用户看到什么 | 系统做什么 |
|---|---|---|
| 数据不存在 | 明确提示（不是 500） | 不落脏数据 |
| 外部系统超时 | 可重试提示 | 抛异常让 MQ 重试；已提交部分不回滚 |
| 无权限 | 403 + 原因 | 记录审计日志 |

## 怎么验证（人能照着复现）
1. 前置数据准备：
2. 操作步骤：
3. 观察点：
4. **反例**：违规操作应被拒绝，且提示正确

## 不做什么
- <批量导入 / 历史数据迁移 / 多语言 / 导出……>

## 验收人
- <姓名>，由他对"做完了没有"签字（不能是写代码的 AI）
```

## 三条硬要求

1. **成功条件必须可观测**："功能正常""体验流畅"不算。
2. **必须有反例**：真实问题几乎都出在异常分支。
3. **必须有人签字**：AI 生成 + AI 验收 = 无人验收。

## SRM 里最容易漏的三项

- **数据范围**：员工端与合作伙伴端看到的同一张单子，可见范围不同；漏写会在联调时才发现
- **工作流状态**：单据进入审批后，哪些字段可改、谁能撤回、重复提交怎么处理
- **内部接口契约**：`/internal` 与 srm-feign 的 DTO 必须一一对应，改一边必须改另一边

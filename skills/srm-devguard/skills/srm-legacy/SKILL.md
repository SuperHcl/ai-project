# SRM 旧代码 review 与改造

5019 个文件、81 个 ≥800 行的类，**全量 review 不可能完成**。做法只有三步：选点、单类诊断、限定范围改造。

## 1. 选点：只改"又大又还在动"的

```bash
python -I .archguard/devguard.py audit --top 15
```

排序 = 复杂度（行数/公开方法/依赖）× 变更热度。判据：

- **巨型 + 高频改动** → 优先。它每次需求都在变糟
- **巨型但不常动** → 只在大改时顺手切，不为它单独开重构
- **小而常动** → 通常是缺一层判断，别重写

## 2. 单类诊断：先判断职责，再读实现

```bash
python -I .archguard/devguard.py audit --file SysUserServiceImpl
```

给出行数、公开方法数、依赖数、近期改动次数，以及"从哪里看起"的定向清单。

**看不懂通常不是水平问题，是这类确实没有结构。** L1 只要三样就能判：

| 看什么 | 红旗 |
|---|---|
| 一句话说得清职责吗 | 说不清 → 没有职责，只有历史 |
| public 方法数 | >20 → 不是类，是工具抽屉 |
| import 数 | >60 → 和半个系统耦合 |
| 同类职责的类 | 有 → 先考虑删掉一个，而不是修好两个 |

详细三档法见 [分级 review](./references/review-method.md)。核心：**L1 扫签名 / L2 只审四类风险 / L3 只逐行读本次要改的 50 行。**

## 3. 改造：一个单元一个类

动手前写两行：

```
改完之后这个类负责：<一句话>
改完之后它不负责：<明确排除的>
```

写不出"不负责什么" → 这只是搬家。

顺序：

1. **先固化现状**：对要动的路径写 3–5 条"当前就是这么行为"的测试（特征测试，不是覆盖率）
2. **搬方法 → 再改结构**，两步不同时做
3. **每搬一组跑一次**相关测试，不攒到最后
4. 目标文件**行数必须变小**；没变小说明只是重排

`devguard.py check` 会盯住"基线内文件变大"，所以这一步有机械反馈。

## SRM 已知热点（供选点时参考）

- `base/permission` 一个包 51 个类，混了技术设施、域策略、数据范围、菜单写入四种变化速率
- "附件谁能看"实现了约 20 次，散在 5 个包
- 授权模型 4 套并存：`Sys*` / `Portal*` / `CommonPermission*` / `SupplierPermission*`
- 附件策略、数据范围、导出过滤：都是"每个域各写一遍"的形状

这些不是立刻要改，而是**改任何一处时优先考虑收敛，不要再写第 N 份**。

## 反模式

- 先重构再开发（两件事混一个 PR，review 无法判断风险）
- 大爆炸重命名（巨大 diff，收益为零）
- 往巨型类里加逻辑（腐烂传导给下一批需求）
- 逐行读完 2000 行然后疲劳放过真正的风险点
- 只读代码，不问"这段逻辑对应哪条业务规则"

## 完成条件

改造点由 `audit` 选出并说明理由；目标形态写了两行；每个单元有特征测试保护；目标文件变小；`check` 通过。

# 分级 review（30 分钟得出"该不该改、从哪改"）

## L1 扫（10 分钟/类，不读实现）

只读三样：public 方法签名、类注释、import 列表。

| 问题 | 红旗信号 |
|---|---|
| 一句话说得清职责 | 说不清 → 没有职责，只有历史 |
| public 方法数 | >20 → 工具抽屉，不是类 |
| import 数 | >60 → 与半个系统耦合 |
| 有没有同类职责的类 | 有 → 先考虑删一个 |

## L2 审（只读命中的方法）

按四类风险定向搜，命中才读，不通读：

| 风险 | 怎么找 | 为什么危险 |
|---|---|---|
| 状态归属 | 搜状态字段的 `set` 调用点 | 多处可写 → 状态机漂移 |
| 事务边界 | 搜 `@Transactional`，看它包住什么 | 包住远程调用 → 长事务；多写未包 → 半成功 |
| 异常吞没 | `catch` 后只 log / `return null` / `return false` | 失败被当成功，最贵的一类 |
| 并发幂等 | 锁、`select` 后 `insert`、MQ 重复消费 | 重复提交、重复入库 |

## L3 逐行（只在改动窗口）

只精读本次要改的 50–100 行。对这段要能回答：

- 对应哪条业务规则？（说不出 → 先问业务，别改）
- 改它会破坏谁？（调用方、测试、外部协议）
- 有没有特征测试能证明我没改坏？

## 改造单元 DoD

- [ ] 只涉及一个类或一组内聚方法
- [ ] 改造前有 3–5 条特征测试断言"当前行为"
- [ ] 搬方法与改结构分两步，每步可运行
- [ ] 目标文件行数变小
- [ ] diff 每行都能追溯到本次目标
- [ ] `devguard.py check` 通过

任一条不满足 → 单元太大，继续切。

## 特征测试怎么写

```java
// 注释写清：这是固化现状，不是规格
@Test
void 当前行为_重复提交返回已有记录而不是报错() {
    // given 已有记录
    // when  再次提交同一单据
    // then  返回同一条，状态不变
}
```

价值：改造后有人问"行为变了吗"，你有机械答案。**不要**用它凑覆盖率，也不要在改造后删掉。

## 不要做

- 为了"读懂"而读完全文。读不完是正常的，选点比读全重要
- 在 review 里提风格建议（那是 linter 的事）
- 把"发现问题"变成"顺手修复"，除非它就是本次目标

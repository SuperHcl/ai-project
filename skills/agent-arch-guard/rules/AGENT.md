# ArchGuard 硬约束（自动加载部分）

> 本块由 ArchGuard 安装器维护：它写在 AGENTS.md 里一对 arch-guard 注释标记之间，安装器只覆盖标记内内容，标记外一律不动。
> 本块只放"每个任务都必须知道"的判断依据；细则按需读 `.arch-guard` 目录下对应 SKILL。

## 1. 方案先行

非单行改动（新增模块、改公共契约、重构、跨域调用）必须先交 `ADR-lite`，**未确认不写代码**。
`ADR-lite` 上限 1 页，字段固定：问题 / 约束 / 备选(2–3) / 选定与理由 / 接口契约+3 个调用示例 / 非目标 / 风险与回滚 / 开放问题。
方案里**禁止**出现"后续可能需要""为了扩展性预留"这类无触发条件的表述——写不出具体触发条件即删除该项。

## 2. 抽象预算

新增接口、抽象类、策略、工厂、泛型基类前，必须给出三行证明：

1. 现有实现/调用方有几个（<2 且无排期中的第二个实现 → 禁止新增）
2. 第二个实现出现的**具体触发条件**（不是"以后可能"）
3. 内联后代码会增加几行（<20 行 → 优先内联）

禁止为单一实现建接口、建 `Factory`、建 `AbstractXxxSupport`。

## 3. 测试预算

一条测试必须能回答"哪条业务规则变化会让它失败"。答不出 → 禁止新增。
必须写：业务规则与边界、外部契约（SQL/序列化/协议）、曾出过 bug 的场景、权限 allow/deny 矩阵。
禁止写：getter/setter、纯字段转换、私有方法、只断言协作者被调用次数、"证明旧类不存在"。

## 4. 边界与判定归属

- 新增跨包依赖必须说明方向与理由；反向依赖一律先讨论再动手。
- 权限/鉴权判定只允许出现在 `pep` 层（统一入口）；业务 service 内**禁止**直接读当前登录用户做判定。
- 同一横切关注点（附件访问、数据范围、导出过滤）已有实现时，必须复用或收敛，禁止再写第 N 份。

## 5. 交付契约

交付必须同时给出四项，缺一项不算完成：

1. **差异**：改了哪些文件、为什么
2. **证据**：`verify.py` 结果 + 实际执行过的命令与输出
3. **review 导航**：建议先看哪三处、哪些目录可跳过
4. **不确定性清单**：哪几处是猜的、悄悄简化了什么、哪些没验证

`verify.py` 未通过不得声称"完成"。禁止交"我做了什么"的叙事文档——那是 diff 的中文复述。

---

**这些约束在生效，如果：** 方案能一页读完、新增抽象都有证明、测试能说出对应的业务规则、diff 每行都能追溯到需求、交付时先给 review 导航再给结论。

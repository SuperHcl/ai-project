# 新需求：四道门

> 本项目已有设计/开发流程（如 BizFlow-8、项目自己的 `.agent/` 规范）。**本 Skill 不重复那些步骤**，只加四道它们没有的门：验收口径、范围预算、落位检查、交付契约。

新需求出问题的根因通常不是写错，而是**一次做太多**：把"完整版"当成"第一版"，顺手加字段、加表、加接口，交付时一大坨没法评。

## 第 1 门：先写验收口径（不写不设计）

在写任何代码前，用 [验收口径模板](./references/acceptance.md) 写清五件事：**谁用、什么数据、成功长什么样、失败怎么办、怎么验证**。

判据：验收口径里出现"支持扩展""兼容后续"这类词 → 范围没定，退回需求。

**禁止**用单元测试代替验收口径。测试证明代码按你写的逻辑运行，不证明业务要的是这个。

## 第 2 门：范围预算

每次改动量四个数：文件数、新增行、新增端点、新增表。默认上限写在 `.arch-guard/budget.json`：

```bash
python -I .arch-guard/scope_check.py --root .              # 交付前必跑
python -I .arch-guard/scope_check.py --root . --base origin/main
```

超限的处理顺序是**砍需求**，不是改预算。确实要改预算，必须写一句理由并让人确认。

经验值：一次评审能看进去的上限约 400 行生产代码 / 5 个端点 / 2 张表。超过就该拆成两次交付。

## 第 3 门：落位检查（写代码前先回答）

| 问题 | 不合格的信号 |
|---|---|
| 放哪个包？现有同类在哪？ | 说不出现有同类 → 先找，别新建 |
| 照哪个范本写？ | 指不出一个现有模块 → 说明这批代码会自成一派 |
| 要不要新增抽象？ | 答"要" → 停，走 `archg-budget` 交三行证明 |
| 要动已有巨型类吗？ | 要动 → 先把本次要改的方法切出去，再在新类里改 |

**改动落位一旦偏离既有结构，就必须在方案里显式说明理由。** 不允许"AI 觉得这样更好"。

## 第 4 门：交付契约

按顺序交四项，缺一项不算完成：

1. **差异**：改了哪些文件、每个为什么
2. **证据**：`scope_check.py` + `verify.py` 输出，以及实际跑过的命令
3. **review 导航**：先看哪三处、哪些目录可跳过
4. **不确定性清单**：哪几处是猜的、简化了什么、哪些没验证

## 反模式

- 一次做"完整版"，把第一版做成终版
- 顺手加字段 / 加表 / 加接口，理由都是"以后要用"
- 用单元测试数量代替验收口径
- 交付时不给评论导航，让人从第一行读起
- 需求里没提但"顺手优化"的改动（必须单独提，不许夹带）

## 完成条件

验收口径已写且人确认；`scope_check.py` 通过；落位四问都有答案；交付四项齐全。

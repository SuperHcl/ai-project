# 腐烂棘轮（ratchet）

老项目不可能先重构再开发。可行的是：**不要求任何人现在就清理，只保证它不再变大。**

## 什么时候用

- 首次接手一个已明显腐烂的仓库（`*Impl` 动辄数千行、一个类几十个方法）
- 需求要求往已知的巨型类里加逻辑
- 团队反复在 review 里说"又变大了"，但没有机制

## 三步落地

```bash
# 1. 记录现状（只记录，不判失败）
python -I .arch-guard/ratchet.py --init

# 2. 提交 baseline，接入交付自检
python -I .arch-guard/verify.py --fast

# 3. 可选：装 git pre-commit（与已有 hook 冲突时会拒绝，不会覆盖）
python -I <plugin>/scripts/install.py --project . --with-hook
```

`--init` 只把**已超标**的文件纳入基线（默认 ≥800 行）。基线里没有的文件，新增时按新文件上限（默认 600 行）判定。

## 规则

| 情况 | 结果 |
|---|---|
| 基线内文件变小 | 通过，提示可 `--update` 收紧 |
| 基线内文件变大 | **阻断** |
| 基线内文件被删除 | 通过，提示可 `--update` 清理 |
| 新增文件超过上限 | **阻断**，要求拆分 |
| 想合法抬高基线 | 必须 `--update --force-raise`，且由人确认 |

`--update` 只会**降低**记录值并收编新超标文件；要抬高必须显式 `--force-raise`，这是刻意设计的摩擦。

## 配合开发的正确姿势

- 要动巨型类时，**先抽出本次要改的方法到新类**，再在新类里改。原类变小，基线自动收紧。
- 禁止为了"顺手统一格式"重排整个文件——会产生巨大 diff 且不减小基线。
- 禁止把新功能塞进已有巨型类：这会触发阻断，且把腐烂传导给下一批需求。
- 重构 PR 与功能 PR 分开；混在一起会让 review 无法判断风险。

## 不要做的事

- 不要用一刀切的"禁止超过 N 行"卡全仓库——存量会全线失败，团队会直接绕过门禁。
- 不要为了让基线通过而删测试或注释。
- 不要在没有基线的情况下先开启阻断。

## 完成条件

`ratchet.py --init` 已生成并提交 baseline；`verify.py --fast` 通过；本次改动没有让任何基线文件变大；新增文件均在上限内。

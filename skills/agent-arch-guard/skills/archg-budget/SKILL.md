# 抽象预算与测试预算

AI 的通病不是写错，是**多写**。多写的东西在 review 时最贵，因为它看起来对。
本 Skill 用配额和证明替代"请保持简洁"这类无效劝告。

## 一、抽象预算

新增任何抽象前，填这张表；填不全就是过度设计。

| 新增物 | 必须证明 | 自动判定 |
|---|---|---|
| 接口 / 抽象类 | 现有实现或调用方 ≥2，或第二个实现的**具体触发条件已排期** | `scan_design.py` 单实现清单 |
| 策略 / 工厂 | 存在 ≥2 条真实分支，且分支来自业务而非技术洁癖 | 同上 |
| 泛型基类 | 已有 ≥3 处形态一致的重复 | 重复代码检测 |
| 新包 / 新模块 | 有自己的不变量与独立变化速率 | 人工 |
| 开关 / 配置项 | 有明确的关闭场景和负责人 | 人工 |

**三行证明模板**（贴在方案或提交说明里）：

```
现有实现：<N 个，列出名字>
第二个实现触发条件：<具体事件 + 时间点，不是"以后可能">
内联代价：<删除该抽象后代码增加 N 行>
```

任一行写不出 → 内联实现，禁止新增。

**常见反例**：只有一个实现的 `XxxStrategy`、只有一个子类的 `AbstractXxxSupport`、只转调一次的 `XxxManager`、包一层只为"以后换实现"的 `XxxClient`。

## 二、测试预算

一条测试必须能回答：**哪条业务规则变化会让它失败？** 答不出就删。

| 必须写 | 禁止写 |
|---|---|
| 业务规则与边界值 | getter / setter / 纯字段赋值 |
| 外部契约：SQL、序列化、协议、字段名 | 纯 MapStruct / BeanUtils 转换 |
| 曾经出过 bug 的场景（有 issue/工单号） | 私有方法、内部调用顺序 |
| 权限 allow / deny 矩阵 | 只断言 `verify(mock)` 被调用 N 次 |
| 并发、事务、幂等边界 | "证明旧类不存在 / 旧表已删" |

补充规则：

- 不为覆盖率写测试。覆盖率只看**变更行**上的业务分支。
- 不用 mock 冒充真实环境。mock 通过不等于集成通过，必须分别标注。
- 测试名必须能读出业务规则（`不允许重复提交同一单据`），禁止 `test1` / `shouldWork`。

## 三、怎么用脚本兜底

```bash
# 列出所有单实现抽象（候选，不是判决）
python -I .arch-guard/scan_design.py --src <源码根>

# 在 CI 里把单实现抽象当失败（项目稳定后再开，先期只报告）
python -I .arch-guard/scan_design.py --src <源码根> --strict
```

脚本只能发现"结构上可疑"，**不能**判断"业务上是否必要"。它负责给出候选清单，人负责给结论。

## 完成条件

每个新增抽象都有三行证明；每条新增测试都能说出对应的业务规则；`scan_design.py` 的单实现清单里没有本次新增项，或已逐项说明理由。

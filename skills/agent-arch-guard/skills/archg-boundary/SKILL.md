# 架构边界与判定归属

架构不是分层口号，是四件可写下来、可被断言的东西：**不变量、边界、依赖方向、判定归属**。
说不出这四件，"架构设计"就是画图。

## 第 1 步：画域地图（不超过 1 页）

对每个域回答四问，缺一不可：

| 问题 | 用途 |
|---|---|
| 这个域的**不变量**是什么 | 决定哪些类可以随便改、哪些不能 |
| 哪些类**禁止**被域外引用 | 边界从口头变成断言 |
| 哪些东西会一起变 | 决定分包；一起变的东西不该被包边界隔开 |
| 依赖方向：谁可以依赖谁 | 决定是否引入反向依赖 |

模板与完整示例见 [域地图与断言模板](./references/domain-map.md)。

## 第 2 步：定依赖方向，并写成断言

依赖方向必须能被构建期检查，否则三个月后必然反转。最小断言集（ArchUnit 或等价物）：

- 域内 `permission/**`、`security/**` 只允许依赖统一的 `model` / `policy` 包，**域之间禁止互引**
- 判定逻辑只允许出现在统一入口（`pep`），业务 service 禁止直接读当前登录用户
- 旁路（只校验登录）必须登记在白名单文件里，测试断言**条目数不增长**

## 第 3 步：收敛重复，而不是各写一份

判断"是不是重复造轮子"的信号：**同一后缀的类出现在 3 个以上不同包**。

处置顺序：

1. 先抽**共享模型**（主体/动作/资源/范围四元组这类），不抽接口
2. 再抽**组合子**（`sameOrg()`、`participant()`、`roleIn()`、`selfOnly()` 这类可拼装谓词）
3. 最后才是**注册表**（按业务类型分发）；注册表是容器，不是设计本身

反例：每个业务域各写一个 `XxxAccessPolicy`、各建一个 `XxxRegistry`——这是在正确方向上重复犯同一个错。

## 第 4 步：迁移不重写

老系统只有一条可行路径：**加适配层，逐步替换，永远不整体重写**。

1. 合并概念（枚举、主体定义、范围定义）——只加适配，不改行为
2. 引入单一决策入口，内部仍调旧代码
3. 抽取组合子，把散落的实现收敛成声明式
4. 上断言锁边界，再删旧代码

每一步都必须可独立交付、可回滚；任何一步要求"全部改完才能跑"就是错的。

## 反 AI 腔清单

- 禁止输出只有层次名的"架构图"（controller / service / dao 这种图不携带任何信息）
- 禁止"高内聚低耦合""单一职责"这类结论，除非紧跟一条可断言的规则
- 禁止为尚未出现的第二个实现设计扩展点
- 给出结论必须附**代价**：这样改之后，哪些东西会变难

## 完成条件

域地图四问都有答案；依赖方向有对应断言（或明确记为待补）；重复实现有收敛方案而非新增一份；迁移路径可分段交付。

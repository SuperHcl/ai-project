# 方案先行（ADR-lite）

目标：把"方案难懂、文档太长、review 吃力"变成一份**一页纸、可判定、可交付**的东西。

## 适用判定

| 请求 | 处理 |
|---|---|
| 新增模块 / 新功能 / 改公共契约 / 重构 / 跨域调用 | 走本流程 |
| 单文件小改、改配置、改文档 | 跳过，直接做 |
| 只是问原理 | 解释完即止，不产出 ADR |

**方案未经人确认，不得开始写实现代码。** 先否掉一个方案的成本接近于零，事后否掉 2000 行不是。

## 第 1 步：写不变量，而不是画模块图

用不超过 10 行回答：这个模块**永远为真**的规则是什么、哪些类**禁止**被外部引用、这份数据**只有一处可写**在哪。
写不出不变量 → 说明还没理解问题，回到需求，不要进设计。

## 第 2 步：至少两个备选，各带代价

只给一个方案的"设计"是销售文案，不是方案。每个备选写三行：怎么做、代价是什么、什么条件下会选它。
禁止"为了扩展性预留""后续可能需要"这类无触发条件的表述——说不出具体触发条件就删掉。

## 第 3 步：落 ADR-lite（上限 1 页）

按 [ADR-lite 模板](./references/adr-lite.md) 输出，字段不得增删。硬性要求：

- **必须给接口契约 + 3 个调用示例**，用代码，不用散文。人读 30 行签名比读 500 行描述快一个数量级。
- 备选方案各占 3 行以内；超过说明在替读者做思考。
- "非目标"必须非空，否则说明边界没想清楚。
- "开放问题"必须写真问题；写"暂无"通常是没审出来。

## 第 4 步：交付时给 review 导航

实现完成后，按以下顺序交付，**先导航后结论**：

1. **差异**：改了哪些文件、每个文件为什么
2. **证据**：`verify.py` 输出 + 实际跑过的命令
3. **review 导航**：先看哪三处、哪些是样板可跳过
4. **不确定性清单**：哪几处是猜的、悄悄简化了什么、哪些没验证

第 4 项是本次交付里最有价值的部分。人 review 的是这份清单和三个风险点，不是整个 diff。

## 禁止

- 交"我做了什么"的叙事文档（diff 的中文复述）
- 一次交超过 400 行生产代码还不拆分
- 在方案里堆砌技术名，却不给触发条件与代价
- 用"建议/尽量/可以考虑"代替"必须/禁止"

## 完成条件

ADR-lite ≤1 页且字段齐全；备选 ≥2 且各有代价；契约含 3 个调用示例；非目标与开放问题非空；交付含四项。**人已确认方案**。

# 旧代码 review 与改造

面对几千个文件，**全量 review 是不可能完成的**。可行的是选点、定形态、单单元改造。

## 第 1 步：选点，不做全量 review

```bash
python -I .arch-guard/audit.py --root . --src <源码根> --top 20
```

按 **复杂度 × 变更热度** 排序。只改"又大又还在动"的；又大但不动的先别碰（改了没收益，风险最高）。

判据：
- **高频改动 + 巨型** → 最高优先，它每次需求都在变糟
- **巨型但不常动** → 只在大改时顺手切，不为它单独开重构
- **小而常动** → 不是结构问题，通常是缺一层判断，别重写

## 第 2 步：定目标形态（改造前必写）

一个改造单元动手前，先写两行：

```
改造后这个文件负责：<职责，一句话>
改造后它不负责：<明确排除的职责>
```

写不出"不负责什么" → 这只是搬家，不是改造。

需要定领域边界时用 `archg-boundary` 的域地图，不要在改造过程中边改边想结构。

## 第 3 步：单单元改造

一个改造单元 = 一个类，或一组内聚的方法。不允许"顺便"改第二个类。

顺序：

1. **先固化现状行为**（特征测试）：对要动的路径写 3–5 条断言"当前行为"的测试。它的作用是防止改造改变行为，不是提高覆盖率。
2. **小步移动**：先搬方法（不改编），再改结构（不搬方法）。两步不要同时做。
3. **每步都可运行**：每搬完一组就跑一次相关测试；不允许攒到最后一起跑。

改造完成判据：**目标文件行数变小**，且 `verify.py --fast` 通过。没变小说明只是重排。

## 第 4 步：分级 review（不要逐行读几千行）

详细操作见 [分级 review 方法](./references/review-method.md)。核心是三档：

| 档位 | 范围 | 时间 |
|---|---|---|
| L1 扫 | public 方法签名 + 类注释 + import | 10 分钟/类，判断职责 |
| L2 审 | 只审风险点：状态归属、事务边界、异常吞没、并发幂等 | 只读命中的方法 |
| L3 逐行 | 只在**本次要改的那 50 行** | 精读 |

L1 就能判掉大部分"看不懂"：**一个类如果 public 方法超过 20 个、且没有一句话能说清职责，它一定有问题**——这个判断不需要读懂实现。

## 反模式

- 先重构再开发（两件事混在一个 PR，review 无法判断风险）
- 大爆炸重命名（产生巨大 diff，收益为零）
- 把新功能塞进旧巨型类（腐烂传导给下一批需求）
- review 时逐行读完 2000 行，然后疲劳放过真正的风险点
- 只读代码不问"这段逻辑对应哪条业务规则"

## 完成条件

改造点由 `audit.py` 选出并说明理由；目标形态写了两行；每个单元有特征测试保护；目标文件变小；review 按三档做，不逐行通读。

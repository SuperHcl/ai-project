# 分级 review 方法

> 目标：用 30 分钟得出"这个类该不该改、从哪改"的结论，而不是花 3 小时读完 2000 行然后疲劳放过真正的风险点。

## L1 扫（结构层，10 分钟/类）

**只读三样东西，不读实现：** public 方法签名、类注释、import 列表。

要回答的问题：

| 问题 | 红旗 |
|---|---|
| 一句话能说清这个类负责什么吗 | 说不清 → 它没有职责，只有历史 |
| public 方法有多少 | >20 → 它不是类，是工具抽屉 |
| import 有多少 | >60 → 它和半个系统耦合 |
| 有没有同类职责的类 | 有 → 先考虑删掉其中一个，而不是修好两个 |
| 依赖方向对不对 | service 依赖 controller、域依赖外层 → 结构反转 |

L1 就能判掉大部分"看不懂"。**看不懂通常不是因为你水平不够，而是因为这个类确实没有结构。**

## L2 审（风险层，只读命中的方法）

不要通读，按风险点定向查。四类风险，命中才读：

| 风险 | 怎么找 | 为什么危险 |
|---|---|---|
| 状态归属 | 搜 `set` 状态字段的位置 | 多处可写 → 状态机漂移 |
| 事务边界 | 搜 `@Transactional`，看它包住了什么 | 包住远程调用 → 长事务；没包住多写 → 半成功 |
| 异常吞没 | 搜 `catch` 后只 log 或 `return null` | 失败被当成成功，最贵的一类 bug |
| 并发/幂等 | 搜 `synchronized`、锁、`select` 后再 `insert` | 重复提交、超卖、重复消息 |

L2 只读命中的方法体，不读全文。**这四类占生产事故的大头**，其余问题都可以等。

## L3 逐行（只在改动窗口内）

逐行精读的范围是**本次要改的那 50–100 行**，不是整个文件。

对这段代码要能回答：
- 它对应哪条业务规则？（说不出 → 先问业务，别改）
- 改它会破坏谁？（调用方、测试、外部协议）
- 有没有特征测试能证明我没改坏？

## 改造单元的定义（DoD）

一个改造单元必须同时满足：

- [ ] 只涉及一个类，或一组内聚方法
- [ ] 改造前有 3–5 条特征测试断言"当前行为"
- [ ] 迁移与结构调整分两步做，每步都可运行
- [ ] 目标文件行数变小
- [ ] 没有"顺手"改的无关代码（diff 里每行都能追溯到目标）
- [ ] `verify.py --fast` 通过

不满足任一条 → 这个单元太大了，继续切。

## 特征测试怎么写（不是覆盖率工具）

改造前，对要动的路径写"当前就是这么行为"的断言，粒度到输入输出：

```java
// 注释写清楚：这是固化现状，不是规格
@Test
void 当前行为_重复校验时返回已有的那条记录而不是报错() {
    // given 已有记录
    // when  再次提交同一单据
    // then  返回同一条，状态不变
}
```

它的价值：改造后如果有人问"行为变了吗"，你有机械答案。**不要**用它提高覆盖率，也不要在改造后删掉——它是行为基线。

## 不要做的事

- 不要为了"读懂"而读完全文。读不完是正常的，选点比读全更重要
- 不要在 review 时提"风格建议"（那是 linter 的事，见 `archg-budget`）
- 不要把"发现问题"直接变成"顺手修复"，除非它就是本次目标
